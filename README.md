# News Categories SKILL —— 足球新闻分类打标规范

> 一个给**大模型**使用的、机器可校验的足球新闻「分类 + 实体打标」知识包。目标读者不是人类编辑，而是**任意一个大模型**：模型读完本目录的文档后，应能对任意一篇足球新闻文章，输出结构稳定、可被程序二次加工的标注结果。

---

## 1. 这个 SKILL 是做什么的

给一篇足球新闻文章，产出**结构化标注结果**，回答两个互相独立、又必须组合使用的问题：

1. **主题（theme）**：这篇文章是什么「体裁 / 话题」？（例如：比赛报道、转会与合同、深度分析……）
2. **实体（entities）**：这篇文章关于「谁 / 什么比赛」？（例如：某球员、某球队、某赛事、某教练、某机构）

标注结果是一个 JSON 对象，供下游系统做**程序化处理**（聚合、检索、归一化、建模）。因此本 SKILL 的最高原则是：

> **一致性、确定性优先**。同一条新闻，无论由哪个模型、在哪个时刻标注，结果都应当一致；标注结果必须能通过 JSON Schema 硬校验。

它不是给人看的分类说明，而是一套**可被机器执行的规范 + 校验契约**。

### 核心设计：双轨制 + 只打重点

- **主题单主类**：一篇文章只有一个 `theme.name`（九选一），可带 1–2 个 `theme.sub` 子类（子类必须来自该主类的闭包枚举）。
- **实体是列表**：`entities` 是**加法式**标签列表，一篇文章可以有多个实体，每个实体带一个 `importance` 重要级别。
- **只打重点（边缘不收录）**：实体**无数量上限**，但只打「重点」。重点按「第一信息价值」分四级，**前三级一律打、第四级一律不打**：

| 级别 | 含义 | `importance` 枚举值 |
| --- | --- | --- |
| 第 1 级 · 第一优先级 | 《组合规则.md》标注「优先」的实体 | `required` |
| 第 2 级 · 核心论断对象 | 文章核心论断的主体（被预测/被报道的主角） | `core` |
| 第 3 级 · 显著提及 | 标题/导语出现，或正文反复出现 | `significant` |
| 第 4 级 · 边缘提及 | 正文一次带过、仅作背景/举例 | **不收录** |

## 3. 给大模型的学习路径

按下面顺序阅读，即可学会本 SKILL。每步都说明「这一步要学到什么」。

1. **README.md**（本文件）—— 建立整体认知：任务是什么、输入输出是什么、有哪些文件。
2. **SKILL.md** —— 了解版本、变更记录、「主题 + 实体」双轨制，以及打标流程的五步。
3. **主题.md** —— 记住**九大主类**和每个主类的**子类枚举**；这是 `theme.name` / `theme.sub` 唯一合法的取值集合。
4. **实体.md** —— 记住**八种实体类型**（`event` / `team` / `player` / `coach` / `organization` / `referee` / `executive` / `agent`）与**命名规范**（简体中文、人名用完整音译名「名·姓」、球队/赛事/机构用官方中文全称、赛季格式 `YYYY` 或 `YYYY-YY`）。
5. **收录标准.md** —— 学会**主题归属**：每个子类什么算、什么不算（正反例）；遇到「一篇文什么都沾一点」时，用第二部分「优先级打分表」裁决唯一主类。
6. **组合规则.md** —— 学会**实体下限**：每个「主题 + 子类」优先/应该打哪些实体（第一优先级 vs 可选）。
7. **通用规则.md** —— 学会**全局硬规则**：`included` 怎么判、只打重点的四级怎么分、去重、命名、枚举合法。
8. **返回结构.md + 返回结构.schema.json** —— 学会**输出契约**：每个字段的含义、必填/选填、`importance` 枚举，以及最终如何跑 schema 硬校验。
9. **金标准样本.md** —— 用**端到端样本**校准：看完整文章如何一步步落到最终 JSON，尤其对照 `reason` 的写法和「只打重点」的取舍。
10. **实体同义词表.md** —— 查表（可选）：遇到高频实体时参考规范名，表内未收录的按《实体.md》命名规范自行输出即可。

> 关键理解：**《主题.md》是主题枚举的唯一事实来源**；**《收录标准.md》是主题归属（边界）的最终裁决依据**；**《返回结构.schema.json》是输出合法性的硬校验**。这三者共同保证「分类正确 + 边界一致 + 输出合法」。

## 4. 输入与输出

### 输入

一篇文章，字段如下（`title`、`body` 必填，其余选填）：

```json
{
  "title": "文章标题",
  "lead": "导语/摘要（可选）",
  "body": "正文全文",
  "source": "来源（可选）",
  "published_at": "发布时间（可选）"
}
```

### 输出

一个 JSON 对象，核心字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `included` | 是 | 是否收录（噪声/非新闻/非足球内容 → `false`） |
| `theme` | 收录时必填 | 主题分类：`name`（九选一）+ `sub`（1–2 个子类） |
| `entities` | 收录时必填 | 实体列表，每项含 `type` / `name` / `importance` / `meta`（选填）/ `remark`（选填） |
| `transfers` | 选填 | 转会关系列表（仅「转会与合同」相关子类） |
| `coach_changes` | 选填 | 教练更迭关系列表 |
| `matches` | 选填 | 比赛关系列表（能确定主客队时） |
| `source` | 选填 | 消息来源（仅原文明确写明时填写，禁止臆造） |
| `reason` | 是 | 打标理由，引用规则锚点，不能为空 |

**不收录**时：`theme`、`entities` 为 `null`，`reason` 说明原因。

完整字段定义与 `transfers`/`coach_changes`/`matches` 的结构见 `返回结构.md`，硬校验见 `返回结构.schema.json`。

## 5. 打标流程（五步）

1. **判 `included`**：是否收录（见《通用规则.md》第 1 条）。不收录 → 直接输出不收录分支。
2. **判主类 → 选子类**：`theme.name` 九选一，`theme.sub` 从该主类子类枚举里取 1–2 个（见《主题.md》《收录标准.md》）。
3. **打实体标签**：按《组合规则.md》的优先/可选，`name` 遵循《实体.md》命名规范，`importance` 按「只打重点」四级（见《通用规则.md》第 4 条）。
4. **写 `reason`**：说明「为什么这样判」，引用规则锚点（如 `《收录标准.md》<主类>·<子类>·正面示例`、`《组合规则.md》…`、`《通用规则.md》第 N 条`）。
5. **跑校验**：用 `返回结构.schema.json` 对输出做硬校验，不通过即不合格。

---

## 6. 范围边界（本 SKILL 不做什么）

- **不负责**跨文章的实体归一化 / 去重 / 对齐实体 ID（由下游系统负责）。
- **不负责**用户自有数据库（第一优先级规范名来源）上线后的刷新与实体 ID 对齐；当前以「中文维基百科 + Wikidata」静态生成《实体同义词表.md》为准（见《实体.md》第 0 节）。
- 只保证**单篇内**的命名规则与一致性。

---

## 7. 快速自检（打标前默念）

- 主题是否**唯一**？子类是否来自同一主类的闭包枚举？
- 实体是否**只打重点**？`importance` 是否合法（`required`/`core`/`significant`）？
- `name` 是否用**全称**（人名「名·姓」、球队/赛事/机构「官方中文全称」）？
- 同一实体是否**只出现一次**？是否**去重**？
- `reason` 是否**引用规则锚点**而非空泛复述？
- 最终输出能否通过 `返回结构.schema.json`？
